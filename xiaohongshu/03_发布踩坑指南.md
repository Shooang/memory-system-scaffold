# 小红书 Skill 审核不通过？我踩过的 7 个坑，帮你一次过审

大家好，我是最近在小红书折腾 Skill 的独立开发者。

前前后后提交了 4 次才过审，
每次都是"未通过"，又不说清楚哪儿有问题。
踩了一堆坑，终于摸清楚了平台的审核偏好。

今天把我踩过的坑全列出来，
帮你少走弯路，一次过审 👇

---

## 先说说背景

最近小红书开放了 Skill 上传功能，
就是那种可以把你的工作流、方法论做成 AI 技能，
直接在小红书里分享给别人用。

我做了一个"AI记忆助手"的 Skill，
想着分享给大家用，
结果连续被打回来 3 次。
每次原因都不一样，每次都得猜。

折腾了快一周，终于过了。
今天把经验总结一下，都是血和泪的教训。

---

## 坑 1：名字用英文，直接被拒

**我踩的坑：**
最开始 Skill 名字叫 "memory-system"，全英文。
提交上去直接打回来，连原因都没怎么说。

**为什么不行：**
小红书 Skill 的面向用户是中文用户，
名字、描述必须是中文的。
全英文的名称，审核直接不通过。

**怎么改：**
- 名称改成中文，比如"AI记忆助手"、"项目记忆助手"
- 描述也要全中文，从用户角度写
- 不要中英混排，也不要用英文缩写当名字

**避坑提醒：**
Skill ID（标识符）可以用英文，
但显示给用户的 name 和 description 必须是中文。

---

## 坑 2：描述太技术，用户看不懂

**我踩的坑：**
最开始的描述是这样写的：
"生成 Knowledge OS 级白盒记忆系统，支持目标栈、SoT 层级、三级召回、生命周期治理..."

审核直接打回来。
现在想想也是，普通用户谁看得懂啊。

**为什么不行：**
Skill 是给普通用户用的，
不是给开发者看技术文档。
描述要说人话，讲清楚"能帮我干什么"。

**怎么改：**
- 从用户痛点出发："让 AI 记住你的项目，做任务再也不跑偏"
- 说清楚能解决什么问题，不要说技术术语
- 用大白话，别拽名词
- 不要用"赋能""抓手""闭环"这种词

**参考模板：**
❌ 错："基于 Knowledge OS 架构的分层记忆系统，支持 SoT 仲裁与三级加载"
✅ 对："帮你给项目搭一套记忆系统，让 AI 记住目标和规则，做长任务不跑偏"

---

## 坑 3：功能描述太绝对，涉嫌夸大

**我踩的坑：**
写了"AI 再也不会忘记"、"长任务绝不跑偏"、"效率提升 10 倍"。
结果被打回来，说功能描述夸大。

**为什么不行：**
小红书对"绝对化表述"查得很严，
尤其是 AI 相关的，不能吹得太神。
什么"10 倍效率""再也不会""必用神器"，
都是高风险词。

**怎么改：**
把绝对化表述改成温和的说法：
- "AI 再也不会忘" → "帮助 AI 记住关键信息，减少遗忘"
- "绝不跑偏" → "降低跑偏概率"
- "效率提升 10 倍" → "帮助提升效率"
- "神器" → "工具" / "助手"
- "必用" → "可以试试" / "推荐"

**避坑提醒：**
保守一点总没错。
宁肯说少一点，也别说太满。
审核过了再说，总比被打回来强。

---

## 坑 4：放了外部链接，直接判定引流

**我踩的坑：**
README 里放了 GitHub 仓库地址，
还有官方文档链接。
审核直接说"第三方引流"，打回来。

**为什么不行：**
小红书对站外引流查得非常严，
任何外部链接都不行，
包括 GitHub、个人网站、公众号、微信群...
哪怕是技术文档链接也不行。

**怎么改：**
- 删除所有外部链接，一个都不留
- 不要提其他平台的名字（比如某个 IDE、某个 AI 工具）
- 不要引导用户去别的地方找更多信息
- 所有说明都写在 Skill 自带的 README 里

**避坑提醒：**
连"搜索 XXX 了解更多"这种都不行，
必须完全没有引流嫌疑。

---

## 坑 5：提到了其他平台/工具

**我踩的坑：**
README 里列了支持的 AI 工具列表，
还写了安装路径，比如"放在 .trae/skills/ 目录下"。
结果又被打回来了。

**为什么不行：**
提到其他平台名称，
也可能被判定为"第三方引流"或者"引导到其他平台"。
哪怕你只是说"兼容 XX 工具"，也可能有风险。

**怎么改：**
- 不要提具体的 AI 工具名称
- 统一说成"支持本地 Skill 机制的 AI 工具"
- 删除特定平台的安装路径说明
- 不要说"在 XX 工具里怎么用"

**参考改法：**
❌ 错："支持 TRAE、Cursor、Codex、Claude Code 等平台"
✅ 对："兼容所有支持本地 Skill 机制的 AI 工具"

---

## 坑 6：Skill ID 删了不能马上用同一个

**我踩的坑：**
第一次提交没通过，我把那个版本删了想重新提交，
结果提示"Skill ID 已存在"。
删了也不能马上用同一个 ID，得等很久或者换个新的。

**为什么不行：**
小红书 Skill 的 ID 是唯一的，
删除后并不会立即释放，
可能要等很久才能重新用。

**怎么改：**
- 第一次就想好 ID，不要随便删
- 如果删了想用同一个，可能要等很长时间（我等了一天还是不行）
- 保险起见，换个新的 ID 重新提交

**我的教训：**
最开始叫 memory-system，删了之后用不了，
换成 memory-os，又删了又用不了，
最后换成了 project-memory。
建议第一次就选好，别像我一样折腾。

---

## 坑 7：文件带了一堆开发者用的东西

**我踩的坑：**
最开始把 GitHub 上的整个目录都上传了，
包括 LICENSE、.gitignore、安装脚本什么的。
结果被打回来，说有违规文件。

**为什么不行：**
SkillHub 只接受"运行必需"的文件，
开发者辅助文件（LICENSE、.gitignore 等）会被拒绝。

**怎么改：**
上传包只留核心文件：
- SKILL.md（必需）
- README.md（可选，用户文档）
- 其他运行必需的文件

删除这些文件：
- LICENSE
- .gitignore
- install.sh / install.ps1 安装脚本
- 测试文件
- 其他开发者用的辅助文件

**避坑提醒：**
如果你想开源，
可以把完整的项目（包括 LICENSE 等）放在 GitHub，
但上传到 SkillHub 的版本，只留运行必需的。

---

## 我的过审 Checklist

总结一下，提交前对照检查：

- [ ] 名称是中文，用户能看懂
- [ ] 描述是中文，从用户角度写，讲清楚能干什么
- [ ] 没有绝对化表述（"再也不会""10 倍""神器""必用"）
- [ ] 没有任何外部链接（GitHub、官网、公众号...）
- [ ] 没有提到其他平台/工具的具体名称
- [ ] 没有营销话术、引流引导
- [ ] Skill ID 是新的，之前没删过同名的
- [ ] 上传包里只有运行必需的文件
- [ ] 没有 LICENSE、.gitignore 等开发者文件
- [ ] 没有安装脚本

---

## 最后想说的话

小红书 Skill 审核其实不算严，
主要是要符合平台规范：
说人话、不夸大、不引流、纯工具。

第一次没过很正常，
根据打回来的原因改，
一般 2-3 次都能过。
